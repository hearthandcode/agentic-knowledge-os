# Refined Agentic Knowledge OS design

## Design thesis

An agentic knowledge operating system should govern transformations of meaning and state, not merely provide folders and persona prompts. Its smallest coherent architecture has three layers, three planes, a typed fleet, and independent human gates.

```text
human orientation
  -> L1 semantic record
  -> L2 typed work and Core8 transformations
  -> review and human decision
  -> L3 host projection
  -> separately authorized effect
  -> evidence and receipt returned upstream as a proposal
```

## Three layers

### L1 — Semantic layer

L1 contains literal source, accepted vocabulary, named meaning owners, human decisions, and policy. It is the layer at which a person can accept an interpretation. The system may propose changes to L1 but cannot silently write them back.

### L2 — Operational layer

L2 contains the public type kernel, Core8 transformations, delegation envelopes, work-item states, diagnostics, evidence, and return contracts. It coordinates work without changing L1 authority. Operational Intelligence lives here as a comparison method: it can inspect state, drift, loss, transition validity, and return readiness.

### L3 — Host-projection layer

L3 adapts the portable contract to a harness such as Hermes, Pi, or a future accepted Exocore interface. Every adapter declares its instruction surface, omissions, compatibility status, review state, and runtime effect. A host projection is not activation, and runtime evidence does not amend L1 automatically.

## Three planes

- Knowledge plane: sources, literal records, normalized proposals, evidence, decisions, projects, and lineage.
- Control plane: constitution, type registry, role contracts, state machines, delegation, gates, and receipts.
- Effect plane: filesystem writes, host configuration, providers, credentials, publication, deployment, messaging, spending, and deletion.

The control plane may describe the effect plane but cannot authorize it. The knowledge plane may inform a decision but cannot manufacture one.

## Orientation before installation logic

The installer can create control surfaces, but the person's extended mind is not initialized semantically until a human orientation occurs. The generated `.akos/ORIENTATION.md` asks for purpose, source ownership, literal-versus-interpreted boundaries, semantic mode, audience, sensitivity, allowed effects, lead role, and return conditions.

The orientation result should be a candidate typed record. Literal answers remain separately addressable; proposed vocabulary is marked as proposal; accepted meanings require an explicit human disposition. Missing answers produce local holds, not personality inference.

## Constitution and type kernel

`AGENTS.md` is prose law with stable `AKOS-RFC-0001.x` clause identifiers. `.akos/operating-policy.json` exposes the semantic modes, L1/L2/L3 distinction, Operational Intelligence limits, and independent gates. `.akos/type-kernel.json` closes the vocabulary used by transformations.

The prose and machine layers have different jobs:

- prose explains purpose, semantics, precedence, and judgment boundaries;
- types constrain inputs, outputs, relations, nullability, and failure behavior;
- tests establish only declared structural predicates;
- the human owner decides meaning, acceptance, and effect release.

If prose and a schema conflict, the dependent transformation holds for review; the schema does not silently win.

## Independent gates

The system keeps six decisions separate:

1. source intake;
2. semantic acceptance;
3. artifact acceptance;
4. local workspace apply;
5. host activation;
6. external effect.

A successful earlier gate never implies a later one. This makes it possible to install a source distribution without enabling a provider, accept a note without publishing it, or validate a schema without declaring its meaning correct.

## Refined build sequence

1. Complete human orientation and record unresolved boundaries.
2. Select one primary Core8 transformation by attention signal and admission test.
3. Bind direct sources and the smallest sufficient context.
4. Produce L2 typed proposals with explicit loss, uncertainty, and failure returns.
5. Review independently where consequence or ambiguity warrants it.
6. Ask the human owner for the exact next gate.
7. Project through the selected host adapter without broadening capability or authority.
8. Perform only the released effect and return exact evidence and a receipt.

## What remains outside this phase

The present source does not implement automatic semantic-memory acceptance, model or provider selection, embeddings or retrieval infrastructure, live Hermes or Pi profile registration, Exocore runtime bridging, credential handling, autonomous scheduling, publication, or a claim that the system is generally intelligent or effective. Those are separate designs and release decisions.
